What is changing in the EU

For generated text, marking and detection now belong in the same conversation.

Article 50(2) expressly joins “marked in a machine-readable format” with “detectable as artificially generated or manipulated.” The Code and Commission Guidelines add text-specific detail. The quotations below are exact excerpts; the engineering explanation is deliberately narrower than a legal conclusion.

Scope first. This is an evidence-tracked engineering proof of concept—not legal advice, a Red Hat product feature, a support statement, or proof of EU AI Act compliance. Application to a particular internal-only deployment remains a question for counsel.

The mark must travel

A UI badge or JSON field disappears when somebody copies free-form text. Decode-time watermarking puts a keyed statistical signal into token choices, so the signal can travel with the text—subject to robustness limits.

Detection is a system

The detector needs the same tokenizer, scheme, configuration and key. It also needs authentication, failure policy, correlation, observability and a defined way to expose results.

Evidence must stay scoped

A positive result is not proof of truth, safety, copyright, authorship or human identity. A negative result is not proof that a human wrote the text.

How the solution can help

Mark at generation time, verify independently, and keep checking.

The implementation adds two keyed watermark processors to vLLM’s V1 decoding path, keeps detection in a separate CPU service, and places a sampling gateway in front of the internal RHOAI predictor. That creates an evidence loop instead of a one-off demo.

EXECUTED Facts D1, D5, D8 and D10 · current fixed-matrix evidence.

Decode-time marking

KGW and SynthID-Text adjust token selection after model logits are produced and before sampling. Model weights and checkpoints remain unchanged.

Independent verification

A separate detector scores plain text using the matching scheme and server-held key, without requiring a running vLLM engine or GPU.

Continuous validation

N=1 validates every completed response; N=5 validates ordinals 5, 10, 15 and so on at one persistent sampler.

Auditable evidence

Selected records retain IDs, SHA-256 digests, scheme, non-secret key ID, verdict, attempts and timings—not prompt or response text.

The lesson that shaped the workflow

The first result looked excellent. It was wrong.

EXECUTED The wheel registered KGW as an entry point while the server also loaded the same class explicitly. vLLM 0.18.0 instantiated both copies, roughly doubling the intended bias. The project marked the first figures as superseded, removed the duplicate loading path, regenerated the corpora and reran the measurements. “The code ran” was not enough; exact loading and raw evidence mattered. Where the claim stops

The internal path worked. That is not the same as a production solution.

EXECUTED Demonstrated scope. OPEN Production boundaries. Source: facts C8, D5 and D10.

What this implementation demonstrates

  • KGW and SynthID-Text generation through vllm serve.
  • Independent detection with matching scheme and server-held key.
  • Per-request enablement, scheme and non-secret key-ID controls.
  • RHOAI ServingRuntime, InferenceService and internal predictor execution.
  • Managed-NeMo metadata correlation through an authenticated broker.
  • Strict one-in-N synchronous validation with bounded retry and fail-closed behavior.
  • Hash-only records, bounded metric labels and finite leak scans.

What remains open

  • External KServe/Istio pass-through and an authenticated public entry point.
  • NetworkPolicy, mTLS, caller authorisation, HA and PDB policy.
  • Multi-replica/global ordinals, restarts, rollouts, streaming and asynchronous delivery.
  • Platform-wide retention guarantees and full data-flow threat modelling.
  • Key creation, rotation, application scoping and compromise response.
  • Paraphrase, translation, multilingual, code and structured-output robustness.
  • Larger models, realistic batches, tensor parallelism, quality evaluation and production performance.
  • Red Hat supportability and deployment-specific legal conclusions.
